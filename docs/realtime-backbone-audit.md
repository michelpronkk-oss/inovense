# Realtime backbone audit

Audit performed before the realtime-backbone implementation. This describes the repository as it stood at the start of this task; it does not claim that Google Cloud, Trigger.dev, or production Supabase have been configured or live-tested.

1. **Signal model.** `os_signal_events` stores bounded source facts and dedupes on `(workspace_id, dedupe_key)`. `os_signal_candidates` stores classification, confidence, priority, routing evidence, and one operator key. `src/lib/signals/engine.ts` normalizes, classifies, and routes; `src/lib/signals/store.ts` persists the result and optionally resolves workflows. Raw message bodies are not signal columns.
2. **Revenue Gmail scanner.** `scanRevenueOpportunities` in `src/lib/operators/revenue/scan.ts` handles `manual`, `scheduled`, and `push`. All call the same internal scan and classification loop. Push injects messages fetched from Gmail history; manual and hourly scheduled scans list a bounded recent set. Classification/action preparation is still inline in the shared scan, not a separately exported per-message processor.
3. **Operator routing.** `routeSignalEvent` uses inbound intent classification and `arbitrateSignalOwnership` (`src/lib/workforce/ownership.ts`) to choose one primary operator and optional supporting operators. Operator activation and workspace entitlement gate automatic workflow proposals.
4. **Workflow resolution.** `createWorkflowFromSignalCandidate` plans and validates a workflow against connector capabilities, activation, entitlement, and deterministic dedupe (`src/lib/workflows/store.ts`, `engine.ts`, `identity.ts`).
5. **Action preparation.** `materializeWorkflowStep` creates a bounded prepared action and checks current connector truth and policy before any approval (`src/lib/workflows/materialize.ts`).
6. **Approval creation.** Workflow approval creation uses `os_approvals`, canonical approval scope, policy evidence, and a per-step dedupe key. The legacy Revenue scanner also has its established approval path. The approval API revalidates state and scope before execution.
7. **Execution.** Approved actions run through existing action/provider executors and `os_execution_intents`; provider response, policy, and approval checks remain authoritative. Gmail push does not execute customer-facing actions.
8. **Outcomes.** `os_workflow_outcomes` and `src/lib/workflows/outcome-observers.ts` record observed/influenced/direct outcomes from evidence. Execution is not treated as an outcome.
9. **Trigger tasks.** Relevant existing tasks include `signal-engine-ingest`, `gmail-push-process`, `gmail-watch-renewal`, the Revenue/Client Flow/Operations/Support scans, and `workflow-recovery`. `trigger.config.ts` already targets Node 22.
10. **Scheduled scans.** Revenue reconciliation is hourly (`revenue-operator-daily-scan`, despite its legacy task id); other Operator scans and connector/workflow health jobs remain scheduled fallbacks. Activation and billing gates apply before unattended Revenue scans.
11. **Manual scans.** Authenticated `/api/operators/{operator}/scan` routes call the same operator scanners as scheduled runs. Revenue uses `scanRevenueOpportunities` for both.
12. **Gmail push.** `/api/connectors/gmail/push` verifies an OIDC Pub/Sub token, validates the envelope, resolves `emailAddress` to one connected workspace, then enqueues a Trigger task. It currently has no database provider-event ledger; task payload still contains the mailbox email and notification history id.
13. **Credentials.** `os_connector_credentials` stores encrypted access/refresh tokens, scopes, status, account identity, and provider email. `CONNECTOR_TOKEN_ENCRYPTION_KEY` must remain stable. Trigger jobs resolve credentials server-side.
14. **Connector health.** Provider failures are classified in `src/lib/runtime/provider-retry.ts`; `os_provider_operations` records safe health/retry metrics. Gmail watch/checkpoint state is held in `os_signal_sync_state.cursor`; Revenue status exposes a limited monitoring projection.
15. **Operator state.** Operator activation is stored in `os_operator_triggers`; readiness and actual execution eligibility are separately resolved from connector capability and billing state. Configured does not itself mean active.
16. **Activity.** Product Activity is a normalized read model over approvals, operator runs/logs, workflows, and outcomes (`src/lib/activity/query.ts`). The older `activity_events` table has no workspace key and is not suitable for tenant-scoped realtime delivery.
17. **Supabase Realtime.** No client `.channel()`/`postgres_changes` subscriptions exist in `src`. Authenticated pages load API data on entry; they do not currently refresh from server mutations.
18. **Idempotency.** Existing database guards include unique signal/candidate/workflow keys, workflow step identity, active approval dedupe, and execution-intent/approval claim controls. Gmail history notifications are serialized by a workspace+connector lease and checkpointed with an expected-cursor compare-and-set.
19. **Retry/recovery.** Gmail history pagination is bounded, duplicate/out-of-order notifications are skipped, and 404 history expiry takes a current profile baseline before a full bounded 30-day Inbox reconciliation. Trigger retries, daily watch renewal, hourly scans, connector-health checks, and workflow recovery provide fallbacks.
20. **Concurrency.** Gmail push tasks use a bounded queue and mailbox concurrency key plus a 15-minute database lease that is extended during pagination. Workflow steps and approvals use durable conditional state and uniqueness guards.

## Audit findings

- The business logic is already shared between Gmail push and scans at the `scanRevenueOpportunities` entry point. Replacing that logic would risk the existing approval, entitlement, CRM, and customer-send boundaries.
- Gmail push intake is authenticated and privacy-conscious in logs, but queue acceptance is the only durability boundary: no canonical provider event row exists to recover an acknowledged Pub/Sub delivery after the Trigger run exhausts retries.
- The canonical signal and workflow tables exist, but there is no reusable provider-event ledger/adapter contract for durable intake from future providers.
- Supabase RLS policies are present on current signal/workflow/approval data; there is no Realtime publication or workspace-scoped client subscription layer. The legacy `activity_events` table is intentionally excluded from any client subscription.
- Gmail watch/history code and business processing are locally testable. Real Pub/Sub delivery, Trigger execution, production checkpoint writes, and live multi-workspace Realtime behavior require external configuration and cannot be asserted from repository tests alone.
